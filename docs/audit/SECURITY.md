# Безопасность и конфиденциальность

Дата: 15.11.2026. Исходный commit: `b52dc6849d94baac48c32aa0d35f4e62126f74a2`. Проверка охватывает код этой ветки, изолированные PHP/MySQL тесты и браузерные mocks. Это **не проверка действующей инфраструктуры Beget** и не юридическое заключение.

## Вывод

Экспертная оценка подготовленного кода: **7,5/10**. Минимизация данных, шифрование, отсутствие сторонней отправки, fail-closed флаги и защита панели реализованы разумно. Подтверждённой утечки, SQL injection, обхода авторизации или иной P0 в проверенном коде не найдено. Подготовленные исправления устраняют повторное создание заявок и зависимость очистки от приостановки приёма. Оценка ограничена тестовой средой: эксплуатационная безопасность неизвестна без серверного доступа, проверки прав, логов, резервных копий и процедур сотрудников.

**Рекомендовать запуск реального приёма персональных данных пока нельзя:** `/privacy` и `/consent` явно обозначены как неутверждённые проекты, серверная конфигурация и организационные меры не подтверждены. Предупреждения и отключённые по умолчанию флаги сохранены. Production, реальные заявки и данные пациентов не использовались.

## Что подтверждено в коде и изолированных тестах

- Next экспортирует статику; PHP лежит в `deployment/beget`, вне `public/`. Реальный `config.php` исключён из Git. В tracked коде нет реальных ключей/настроек новой БД; шаблоны содержат заглушки.
- Клиент разрешает реальную отправку только по HTTPS на двух явных доменах клиники, при enabled-флаге и версии согласия. На localhost/Vercel форма демонстрационная; mock-тесты проверяют отсутствие настоящего dispatch.
- API принимает только POST JSON до 4096 байт, проверяет точный Origin, HTTPS-флаг, bool consent и точную версию согласия, типы и длины полей. Имя ограничено буквами/разрешёнными разделителями, телефон нормализуется до `+7` и 10 цифр; источник — enum. Свободные жалобы и диагнозы не собираются.
- Поля уходят только в POST body. Ответ не содержит введённое имя, телефон, SQL или конфигурацию. Клиент не печатает поля в консоль и не добавляет их в URL.
- PDO использует настоящие prepared statements; пользовательские значения не интерполируются в SQL. Динамические интервалы — приведённые к int значения с ограничениями. XSS-текст в контексте услуги остаётся данными и экранируется через `htmlspecialchars` при показе сотруднику.
- Имя, телефон, услуга и врач хранятся в AES-256-GCM ciphertext с nonce 12 байт/tag 16 байт. Ключи — отдельные 32-байт значения из приватного config. Подмена ciphertext отвергается. Индивидуальные ключи и IP не возвращаются браузеру.
- Rate limit — транзакционный MySQL counter с блокировкой строки: 3 новых обращения/1800 секунд и 8 попыток входа/3600 секунд на HMAC IP. Не доверяет клиентскому X-Forwarded-For. Идентичный replay сохранённой заявки не расходует новый слот.
- Уникальный `request_id` защищает от конкурентных повторов. Проверка сверяет также расшифрованный payload и версию согласия; изменённые данные под старым ID не затирают запись. Это не token авторизации и не содержит персональных сведений.
- Админка по умолчанию отключена, требует HTTPS, проверяет password hash; нельзя прочитать заявки без authenticated session. Сессия Strict/Secure/HttpOnly, strict mode, ID обновляется при входе и выходе; после 15 минут неактивности требуется вход. CSRF нужен для login/logout. Ответы no-store, noindex и CSP с frame-ancestors none.
- Ошибка БД даёт generic 503 для формы; панель показывает безопасную ошибку загрузки. Неправильная конфигурация не включает приём автоматически.
- Отдельное согласие на Метрику: до разрешения script не добавляется; счётчик не запускается на preview; webvisor выключен; ручной pageview использует origin+pathname без query/hash. Отзыв выбора устанавливает disable-флаг. Браузерные проверки — полностью замокированные, без связи с реальным счётчиком.

## Применимость advisory зависимостей

Исходный Next 16.2.6 попадал под advisory семейств Server Actions, custom server/rewrites SSRF, cache/ISR poisoning, middleware, Image Optimization SVG/AVIF RCE/SSRF, `next/og`, `use cache`, metadata routes, Windows hosted server и dev MCP. В `out/` нет соответствующего Node runtime: `output: export`, `images.unoptimized: true`; в проекте нет Server Actions, `use cache`, route handlers, middleware и ImageResponse. Поэтому **не подтверждён remote exploit текущего статического размещения**. Риск оставался у build/dev/будущего изменения архитектуры; он не скрыт за этим ограничением. Выполнено обновление в пределах major и повторная проверка сборки. Остаточные moderate относятся к цепочке eslint/typescript tooling; lockfile и audit сохранены, отдельное сопровождение нужно без непроверенных forced overrides.

## Ограничения и дальнейшее сопровождение

Не проверены реальные PHP version/extensions/display_errors, HTTPS/HSTS, Apache AllowOverride/mod_headers, права config/логов/backup, серверные session.save_path/gc, firewall/MySQL exposure, местоположение БД, состав access logs, cron и исполнение retention. `.htaccess` содержит Options -Indexes и заголовки, но фактическое применение на Beget неизвестно. Нельзя утверждать защищённость сервера по файлам в Git.

Rate limiting по IP и JSON honeypot — базовая защита; бот может заполнять валидные поля, распределять IP и оставлять honeypot пустым. Перед реальной нагрузкой нужен согласованный антибот/edge rate policy, не мешающий пациентам за общим NAT. Абсолютный срок сессии не реализован, есть idle timeout. Один общий пароль не даёт персонального отзыва доступа и audit trail; для нескольких сотрудников нужны индивидуальные аккаунты и дополнительные факторы. Такие изменения не выполнялись как незапрошенный инфраструктурный редизайн.

Ключи за пределами public_html уменьшают риск раскрытия файлов; шифрование не защищает от полностью скомпрометированного PHP процесса с доступом к ключу. Автоматическая ротация/идентификаторы версий ключей не реализованы. До запуска нужен согласованный recovery/rotation сценарий, резервная копия ключа отдельно от БД, тест восстановления и минимальные права сотрудникам/процессу. Утеря ключа делает заявки невосстановимыми; перенос нового ключа без controlled re-encryption недопустим.
