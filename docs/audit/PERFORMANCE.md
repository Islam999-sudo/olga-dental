# Производительность: методика и результаты

Дата: 15 ноября 2026. Исходная сборка: `b52dc6849d94baac48c32aa0d35f4e62126f74a2` (Next 16.2.6). Проверенная исправленная сборка: `e3d33759be9b383b492f96624172f3f5d8fa5033` (Next 16.4.6).

## Границы измерения

Проверяется production static export (`next build`, `output: "export"`, `images.unoptimized: true`), а не dev server. Использован настоящий headless Chromium 156.0.8078.79 на Linux; это эмуляция размера экрана, не физическое Android/iOS-устройство. Lighthouse 13.6.0 запускается CLI с четырьмя категориями, без скрытия элементов, блокировки URL и изменения страницы ради оценки. Яндекс Карта остаётся штатным lazy iframe; аналитика на localhost отключена существующим production-host guard.

Локальный сервер — Python `http.server`, HTTP/1.0, без gzip/Brotli/CDN, TLS и сетевого пути Beget/Vercel. Следовательно, localhost TTFB не характеризует hosting, а исходящие байты JS/CSS без сжатия завышают сетевой объём относительно правильно настроенного CDN. Измерения относятся к домашней странице и репрезентативной странице услуги; это не Lighthouse-сертификация всех маршрутов.

Mobile Lighthouse: 412×823, DPR 1.75, Android emulated user agent, `throttlingMethod: simulate`, RTT 150 ms, throughput 1638.4 Kbps, CPU slowdown 4×. Desktop использует штатный `--preset=desktop`; точная конфигурация и benchmarkIndex каждого запуска сохранены в JSON evidence. Новый браузер и очищенное storage для каждого запуска. CPU облачной машины разделяется между задачами: первоначальные параллельные замеры имеют существенный разброс и не используются как доказательство ускорения JavaScript.

CDP-профиль: 390×844, DPR 1, mobile emulation, CPU/network без throttling. Зафиксированы загрузка + 5 s ожидания, отдельное окно 5 s покоя, открытие/закрытие записи и полная прокрутка. Снимки heap — JS heap страницы, не RSS браузера; такой короткий профиль не доказывает отсутствие утечек памяти. CDP TaskDuration не измеряет GPU стоимость blur/compositing.

INP не заявляется: для надёжного полевого INP нужна выборка реальных взаимодействий. Event Timing одного лабораторного клика и Lighthouse TBT приведены с их собственными названиями и не подменяют INP.

## Контролируемое сравнение после исправлений

После завершения остальных браузеров и сборок выполнена последовательная серия на одной машине, без параллельного QA/build: B1 → A1 → A2 → B2 → B3 → A3. B — сохранённый исходный export на `127.0.0.1:4180`, A — окончательный export на `127.0.0.1:4181`. Затем выполнены пары desktop и mobile `/services/caries/` и два CDP-профиля. Каждый Lighthouse запуск — новый browser profile. Ничего не исключалось из измеряемой страницы. До/после — разные версии Next вследствие исправления безопасности, поэтому изменения времени JS нельзя приписывать одному компоненту.

Первый JS heap немного вырос, итоговый снимок снизился; это не основание объявлять исправление или отсутствие утечки. CDP ScriptDuration вырос, а Lighthouse bootup median снизился: методики/периоды разные, универсальное ускорение JavaScript не заявляется. В покое нет непрерывной JS/layout нагрузки, но GPU blur/compositing и JS cross-origin iframe этими main-frame counters не измерены.

При прокрутке обе сборки действительно попытались загрузить Яндекс iframe; в этой среде запрос завершился `ERR_CERT_AUTHORITY_INVALID`. TLS-проверка не отключалась. Поэтому реальный render карты, её полный сетевой вес и поведение при доступном Яндексе остаются непроверенными. Аналитика не загружается штатно на localhost. В профилях также видны отменённые (`ERR_ABORTED`) speculative/prefetch-запросы; проверку доступности самих маршрутов следует смотреть в `REGRESSION.md`.

Экспертная интерпретация: проверенная статическая сборка достигает указанных лабораторных целей на выбранных сценариях, с существенным снижением сетевого веса и сохранением интерфейса. Это не измерение реальных Beget/Vercel latency, production analytics после согласия, Safari GPU или полевого INP.

## Проверяемые артефакты

- `evidence/lighthouse-before.json`: категории, численные аудиты, реальные configSettings/environment, сетевой список каждого исходного запуска; DOM и полные скриншоты Lighthouse не включены в публичный JSON.
- `evidence/cdp-before.json`: навигационные времена, PerformanceObserver, память, запросы и CDP metrics первоначального профиля.
- `evidence/lighthouse-controlled-before.json`, `evidence/lighthouse-after.json`: все 10 контролируемых Lighthouse запусков с конфигурацией/версиями, source commit, request priority и метриками.
- `evidence/cdp-controlled-before.json`, `evidence/cdp-after.json`: два контролируемых профиля с ответами/ошибками сети.
- `evidence/bundle-stats.json`: размеры JS/raw/gzip и изображений, SHA-256 исходного/исправленного статического export. Полный raw Lighthouse HTML/JSON остался в локальном `/tmp/olga-perf/`; публичные JSON исключают DOM-тексты и встроенные снимки.
- Скриншоты до/после и функциональные ограничения перечислены в `REGRESSION.md` и `VISUAL-UX.md`.

## Воспроизведение

Установить вспомогательные инструменты отдельно от приложения, например:

```bash
npm install --prefix /tmp/olga-perf lighthouse@13.6.0
python3 -m http.server 4173 --bind 127.0.0.1 --directory out
```

В другой оболочке:

```bash
CHROME_PATH=/usr/bin/chromium node /tmp/olga-perf/node_modules/lighthouse/cli/index.js \
  http://127.0.0.1:4173/ \
  --chrome-flags='--headless --no-sandbox --disable-dev-shm-usage' \
  --only-categories=performance,accessibility,best-practices,seo \
  --output=json --output=html --output-path=/tmp/olga-mobile
```

Для desktop добавить `--preset=desktop`. Сделать три последовательных mobile запуска и сообщать медиану вместе с диапазоном. Не сравнивать dev и production, тёплый и холодный кэш либо разные throttling presets.

CDP-профиль воспроизводится `tools/performance-probe.mjs` с Playwright из отдельного toolkit (см. `tools/README.md`). Скрипт открывает форму без отправки и прокручивает страницу:

```bash
cp docs/audit/tools/performance-probe.mjs /tmp/olga-qa/
node /tmp/olga-qa/performance-probe.mjs after http://127.0.0.1:4181
```

Результат: `/tmp/olga-perf/after/cdp.json`; каталог меняется через `PERF_OUTPUT`. Сценарий не заполняет и не отправляет заявку.

## Ограничения и следующие действия

После согласования инфраструктуры измерить реальные Beget response headers/compression/cache, HTTPS TTFB и preview на том же сетевом пути. На production получить полевые Core Web Vitals только через согласованный механизм аналитики; данные формы и параметры URL не должны попадать в telemetry. Проверка low-end устройства и iOS Safari требует отдельного реального устройства/среды. Метрика после явного согласия и реальный сетевой вес/плавность Яндекс Карты требуют отдельной проверки на разрешённом домене.
