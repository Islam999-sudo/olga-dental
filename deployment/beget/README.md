# OLGA Dental — отдельная система приёма заявок на Beget (подготовка)

**Статус: ПОДГОТОВЛЕНО К ТЕСТИРОВАНИЮ, НЕ ЗАПУЩЕНО.** Этот каталог не является действующей системой хранения пациентов. Не загружать PHP-код и не включать обработку реальных данных до одобрения документов и проверки инфраструктуры.

## Почему PHP отдельно от Next.js

В проекте установлен `output: "export"`: Next.js создаёт статические файлы в `out/`. Beget исполняет PHP отдельно от этой сборки. Поэтому PHP-файлы находятся в `deployment/beget/`, **а не в `public/`**. Так Vercel не сможет отдать исходный PHP-код как обычный статический файл.

Схема после запуска:

- Браузер на `https://olga-clinic-murino.ru` → `POST /api/booking.php` **на том же домене**.
- PHP валидирует имя, телефон, подтверждение согласия, источник; ограничивает попытки.
- Данные шифруются AES-256-GCM отдельным секретом сервера и сохраняются в новой MySQL-базе.
- Сотрудник открывает `https://olga-clinic-murino.ru/clinic-admin/index.php` по защищённой HTTPS-сессии и отдельному паролю.
- В заявке нет свободного медицинского комментария; на email данные пациента не отправляются. Метрика получает только событие успешной отправки, без персональных полей.
- Тестовая версия Vercel **никогда не отправляет заявки**, даже если конфигурация сборки случайно укажет включить запись.

## Структура пакета

```text
deployment/beget/
├── booking-private/                 # ПЕРЕНОСИТЬ ЗА ПРЕДЕЛЫ public_html
│   ├── bootstrap.php                # соединение, шифрование, rate-limit
│   ├── config.php.example           # ТОЛЬКО ШАБЛОН, БЕЗ СЕКРЕТОВ
│   ├── schema.sql                   # новая отдельная база
│   └── maintenance.php              # периодическая очистка по сроку
└── public_html/                    # копировать соответствующие файлы только на Beget
    ├── api/
    │   ├── booking.php
    │   └── .htaccess
    └── clinic-admin/
        ├── index.php
        └── .htaccess
```

## Порядок работ после восстановления Beget

1. Получить согласование ООО «ОРДВИК» на новый маршрут персональных данных, сроки хранения, текст политики и отдельного согласия. Уточнить статус медицинской лицензии и обязанности перед Роскомнадзором. **Не считать текущие страницы `/privacy` и `/consent` готовыми правовыми документами — это помеченные черновики.**
2. Подтвердить, что **конкретные** сервер и MySQL-база размещены в РФ, выяснить субподрядчиков, условия обработки данных и резервного копирования. Изолированная база сама по себе не гарантирует соответствие 152-ФЗ.
3. В панели Beget создать **новую** базу и отдельного пользователя с правами только на неё. Не использовать существующую базу клиники.
4. Выбрать для сайта PHP 8.2 или новее, проверить расширения `pdo_mysql` и `openssl`. На рабочем сервере должен действовать HTTPS.
5. С помощью SFTP/SSH разместить `bootstrap.php` и `maintenance.php` **в отдельном приватном каталоге** рядом с `public_html`, например:
   ```text
   ~/olga-clinic-murino.ru/booking-private/bootstrap.php
   ~/olga-clinic-murino.ru/booking-private/maintenance.php
   ~/olga-clinic-murino.ru/booking-private/config.php
   ~/olga-clinic-murino.ru/public_html/api/booking.php
   ~/olga-clinic-murino.ru/public_html/clinic-admin/index.php
   ```
   Реальный путь сайта может отличаться: проверьте его в панели. PHP-обработчики вычисляют путь к `booking-private` относительно `public_html`. Не размещайте `config.php` внутри `public_html` **ни при каких обстоятельствах**.
6. Выполнить `schema.sql` в **новой базе**, предварительно создав резервную копию. Создать `booking-private/config.php` на сервере из шаблона (не через GitHub) и установить права доступа только для владельца процесса. Файл не должен попадать в Git.
7. Создать два независимых ключа (по одному запуску для каждого):
   ```sh
   php -r 'echo base64_encode(random_bytes(32)), PHP_EOL;'
   ```
   Создать хеш **уникального** пароля администратора:
   ```sh
   php -r 'echo password_hash("YOUR_LONG_UNIQUE_PASSWORD", PASSWORD_DEFAULT), PHP_EOL;'
   ```
   Не отправляйте пароли, ключи шифрования или доступы в чат. Храните резервную копию ключа шифрования в защищённом месте; без него восстановить зашифрованные заявки будет невозможно.
8. Пока оставить `accept_bookings => false`, а на стороне Next.js — `NEXT_PUBLIC_BOOKING_ENABLED=false`. Провести проверки PHP: `php -l` для каждого файла, проверки доступа, конфигурации БД, шифрования, rate limiting и защиты панели. Провести тестовые запросы **только с вымышленными данными**.
9. Утвердить юридические документы и присвоить **реальный номер версии согласия**, например `2026-11-approved-01`. Внести одинаковую строку в `config.php` (поле `consent_version`) и настройку сборки `NEXT_PUBLIC_BOOKING_CONSENT_VERSION`. Опубликовать утверждённые `/privacy` и `/consent`, удалить предупреждения о черновиках.
10. Собрать обновлённый статический сайт с `NEXT_PUBLIC_BOOKING_ENABLED=true` **только после тестов**, загрузить `out/` на рабочий хостинг по согласованной процедуре, затем отдельно перенести PHP-скрипты в `public_html`. Важно: не запускать автоматическое копирование PHP из `deployment/` в `out/`. После проверки маршрутов включить `accept_bookings => true` в приватном config.php и провести контрольную отправку тестовой заявки.
11. Проверить вход и выход из административной панели, просмотр тестового обращения, блокировку частых повторений, отказ при неверном Origin и неверном согласии, ошибки при недоступной БД; затем удалить тестовые записи, настроить резервное копирование и контроль доступов сотрудников.
12. После утверждения срока хранения настроить плановую очистку `maintenance.php` через cron (только CLI). Сохранить документированную процедуру восстановления и отзыва доступа. Провести внутренний аудит серверных логов: записи веб-сервера тоже могут содержать IP-адреса.
13. **Только после безопасного переключения** отозвать старый Web3Forms access key и удалить неиспользуемые интеграции из действующего сайта. Для отката сохранить отдельный план, не возвращающий реальные данные в Web3Forms без новой правовой проверки.

## Важные ограничения

- На Vercel нет MySQL-БД и PHP-обработчика; невозможно проверить полный цикл до подключения Beget или локальной среды PHP+MySQL.
- Защита от массовых запросов по IP — только базовый уровень; потребуется дополнительная антибот-защита по результатам нагрузки. Серверные логи и резервные копии учитываются в документации по персональным данным.
- Единый пароль для панели — временный вариант для небольшого числа уполномоченных сотрудников. Для нескольких работников следует внедрить отдельные учётные записи, журнал действий и дополнительные факторы авторизации до хранения реальных заявок.
- Реальная система ещё не прошла независимый аудит безопасности или правовую экспертизу. Применять в клинике только после проверки.
